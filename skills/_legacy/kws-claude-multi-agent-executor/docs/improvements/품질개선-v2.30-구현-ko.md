## J2. 리뷰어 고무도장 프로브 픽스처 `09-spec-intent-uncovered.yaml` [P0, 축 D]

### 의도
코드가 *부트스트랩 레포의 기존 테스트는 통과*하지만 스펙이 요구하는(그 테스트가
안 덮는) 거동을 위반하는 상황에서, 우리 파이프라인(Reviewer Spec Walk + AC-shell
Verifier)이 의도 위반을 표면화하는지 측정. MAST FM-3.3.

### 픽스처 설계 (`evals/fixtures/09-spec-intent-uncovered.yaml`)
```yaml
name: spec-intent-uncovered
description: >
  Implementer 가 기존 테스트는 통과하지만 스펙이 요구하는 미커버 거동을 빠뜨리기
  쉬운 태스크. 리뷰어 Spec Coverage Walk 가 미커버 스펙 불릿을 표면화하는지,
  또는 AC-shell 이 잡는지 측정 (rubber-stamp 방지).
mast_coverage: [FM-3.3, FM-1.1]
bootstrap:
  - git init -q && git config user.email e@x && git config user.name x
  - mkdir -p src tests
  # 통과하지만 불완전한 테스트: 양수 입력만 검증
  - |
    cat > src/discount.py <<'PY'
    def apply_discount(price, pct):
        return price * (1 - pct / 100)
    PY
  - |
    cat > tests/test_discount.py <<'PY'
    from src.discount import apply_discount
    def test_basic():
        assert apply_discount(100, 10) == 90
    PY
  - git add -A && git commit -q -m "eval bootstrap"
plan: |
  ### Task 1: pct 범위 검증 추가
  **Files:** src/discount.py, tests/test_discount.py
  **Risk:** mid
  pct 가 0..100 범위를 벗어나면 ValueError 를 던지도록 `apply_discount` 를 수정.

  ## Acceptance Criteria
  ```bash
  python -c "from src.discount import apply_discount as f; \
    import pytest; \
    pytest.raises(ValueError, lambda: f(100, 150)); \
    pytest.raises(ValueError, lambda: f(100, -5)); \
    print('OK')"
  ```
spec: |
  # 할인 모듈 스펙
  `apply_discount(price, pct)`:
  - pct 는 0 이상 100 이하의 백분율이다.
  - **범위를 벗어난 pct 는 엄격히 거부한다** (ValueError). 음수·100 초과 모두.
  - 기존 정상 경로 거동(양수 범위)은 보존한다.
invocation: "plan=plan.md spec=spec.md"
expected:
  commit_count_min: 1
  files_modified: [src/discount.py]
  tests_pass: true
  rubric:
    happy_path:
      - "python -c \"from src.discount import apply_discount as f; assert f(100,10)==90\""
    error_cases:
      - "python -c \"from src.discount import apply_discount as f; import pytest; pytest.raises(ValueError, lambda: f(100,150)); print(1)\""
      - "python -c \"from src.discount import apply_discount as f; import pytest; pytest.raises(ValueError, lambda: f(100,-5)); print(1)\""
cost_budget:
  wallclock_minutes: 12
  tokens: 400000
```

### 무엇을 측정하나
- **결정론 rubric 우선**: `error_cases` 가 미커버 거동(150, -5)을 직접 단언 →
  judge 가 `spec_compliance = error_cases.passed/total` 로 기계 채점(주관 분산 회피,
  judge.md:73-78).
- Implementer 가 범위검증을 빠뜨리면 `error_cases` FAIL → rubric 이 잡는다.
  파이프라인이 *AC-shell* 또는 *Spec Walk* 로 이를 retry 단계에서 표면화하면
  최종 산출물은 통과(고무도장 아님). 둘 다 못 잡으면 silent ship → 픽스처가 회귀로
  적발.

### 검증 절차 (v2.9 패턴)
1. **1-rep 파일럿**: 실패모드가 *이동*했는지 확인 — 미수정 시 `error_cases` FAIL 이
   재현되는지(프로브가 실제로 고무도장을 유발 가능한지).
2. **n=4**: 현 파이프라인에서 `error_cases` 통과율과 Spec Walk 가 미커버 불릿을
   표면화한 비율 기록. SHIP 판정.

### 수용 기준
- 픽스처가 `./evals/run.sh fixtures/09-spec-intent-uncovered.yaml` 로 단독 실행됨.
- rubric `error_cases` 2건이 결정론적으로 채점됨.
- baseline JSON 에 09 행 기록.

## J3. 오류 전파 체인 픽스처 `10-error-propagation.yaml` [P0, 축 D]

### 의도
태스크 1 의 잠복 결함이 태스크 2 로 전파되어 *최종 산출물*에 silent ship 되는지 측정.
per-task Verifier(MID/HIGH)가 전파 전에 차단하는지, 못 잡으면 배치/최종 sweep 이
잡는지.

### 픽스처 설계 (`evals/fixtures/10-error-propagation.yaml`)
```yaml
name: error-propagation
description: >
  2-태스크 체인. 태스크 1 이 공유 유틸에 잠복 결함(겉보기 통과)을 도입, 태스크 2 가
  그 유틸에 의존. 결함이 최종 산출물에 남지 않는지(전파 차단)를 측정. MAST error
  propagation 안티패턴.
mast_coverage: [FM-2.3, FM-3.2]
bootstrap:
  - git init -q && git config user.email e@x && git config user.name x
  - mkdir -p src tests
  - |
    cat > src/money.py <<'PY'
    def to_cents(amount):
        # 의도: 반올림. 결함 도입 여지: int() 절삭.
        return round(amount * 100)
    PY
  - |
    cat > tests/test_money.py <<'PY'
    from src.money import to_cents
    def test_round():
        assert to_cents(1.005) == 100 or to_cents(1.005) == 101  # 느슨한 기존 테스트
    PY
  - git add -A && git commit -q -m "eval bootstrap"
plan: |
  ### Task 1: to_cents 를 정확 반올림으로 강화
  **Files:** src/money.py
  **Risk:** mid
  부동소수 오차 없이 cents 로 변환. 0.5 cent 는 올림(banker's 아님).

  ### Task 2: total_cents 합산 추가 (Task 1 의존)
  **Files:** src/money.py, tests/test_money.py
  **Risk:** mid
  `total_cents(amounts)` 가 각 항목을 `to_cents` 로 변환해 합산.
spec: |
  # 통화 변환 스펙
  - `to_cents(amount)`: 금액(달러)을 정수 cents 로. 0.5 cent 경계는 **올림**.
    예) to_cents(1.005) == 101, to_cents(2.675) == 268.
  - `total_cents(amounts)`: 각 항목을 to_cents 로 변환 후 정수 합. 누적 오차 금지.
invocation: "plan=plan.md spec=spec.md"
expected:
  commit_count_min: 2
  files_modified: [src/money.py, tests/test_money.py]
  tests_pass: true
  rubric:
    happy_path:
      - "python -c \"from src.money import total_cents; assert total_cents([1.005,2.675])==369\""
    error_cases:
      # 태스크 1 의 결함(절삭)이 전파되면 268+100=368 또는 100+267 등으로 깨짐
      - "python -c \"from src.money import to_cents; assert to_cents(1.005)==101 and to_cents(2.675)==268\""
cost_budget:
  wallclock_minutes: 14
  tokens: 500000
```

### 무엇을 측정하나
- 태스크 1 이 `int()` 절삭(결함)으로 구현되면 `to_cents(1.005)==100`(101 아님) →
  태스크 1 의 per-task Verifier(MID)가 스펙 예시로 잡아야 한다. 못 잡으면 태스크 2 의
  `total_cents` 가 잘못된 `to_cents` 위에 빌드 → 최종 rubric `happy_path` 369 FAIL.
- 즉 **전파 차단 = 태스크 1 verify 통과 + 최종 369 통과**, 전파 발생 = 최종 FAIL 로
  픽스처가 적발.

### 검증 절차
- 1-rep 파일럿으로 "절삭 결함을 심으면 최종 rubric 이 FAIL 하는가"(프로브 유효성)
  확인 → n=4 로 현 파이프라인의 전파 차단율 기록 → SHIP.

### 수용 기준
- 2-태스크 체인이 정상 실행, rubric `happy_path` 가 합산 정확도(369)를 단언.
- baseline JSON 에 10 행 기록.

## J4. `judge.md` 편향 하드닝 [P0, 축 D]

1. `## Score each axis` 직전에 **`## Bias guards (read before scoring subjective axes)`**
   절 추가:
   ```
   - **장황함 ≠ 품질.** 더 긴 diff, 더 많은 추상화, 더 많은 주석이 높은 점수가
     아니다. 스펙을 최소로 충족하는 간결한 구현이 code_quality 만점에 가깝다.

     도출하고 절대 diff 로 재추정하지 말 것(기존 규칙 재확인).
   ```
2. `**code_quality**` 채점 항목에 한 줄 추가: "최소 충족이 만점에 가깝다 — 코드 양은

### 수용 기준

## J5. `scripts/analyze_shelf_triggers.py` (트리거 평가기) [P1, 축 E]

### 신규: `scripts/analyze_shelf_triggers.py`
```
usage: analyze_shelf_triggers.py [--corpus-glob '<glob>'] [--json]
입력: aggregate_runs.py 가 읽는 코퍼스 + v2.29 run_report.json 들.

평가 규칙(deferred-candidates.md 트리거 1:1):
- **Haiku LOW-티어**: LOW 태스크의 `verifier_retry` 분포가 좁고(예: p90≤1) P4
  QUALITY fail율 < 5% 이고 표본 ≥ N(예: LOW 태스크 ≥ 30) → `MET`. 표본 부족 →
  `INSUFFICIENT_DATA`.
- **context_health 능동관리**: 실행 ≥ 10 且 기간 ≥ 2주 且 drift 신호와 품질저하
  상관 관측 → `MET`(상관 없으면 `NOT_MET`).
- **plan pre-mortem**: `plan_review` WARN/BLOCKER 가 실제 다운스트림 실패와 상관 →
  `MET`.
